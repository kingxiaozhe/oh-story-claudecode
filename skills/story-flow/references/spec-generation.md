# 流水线初始化与变更模式

## 初始化（新流水线）

前提：项目已有 `设定/` 与 `大纲/`（story-long-write Phase 1-3 的产物）。缺失 → 先引导走 `/story-long-write` 开书，story-flow 不重复实现设定/大纲方法。

**分 Step 执行，每步落盘后再进下一步**（单步生成量过大会撑爆上下文，实测教训）：

### Step 1：核对真值层

清点 `设定/`、`大纲/大纲.md`、`大纲/卷纲_第X卷.md`、`追踪/伏笔.md`、`追踪/上下文.md`、`追踪/角色状态.md`、`设定/文风.md`（或对标文风）。**人物卡逐个核验"台词风格/声口"字段**（语言签名+口头禅+禁语三件套）——声口核对门禁（N4）与声口速记（派发模板）都依赖它，缺失的角色现场补卡。**声音体系三层分工（v0.2.2 统一声明）**：①**作者叙述声口=`设定/声口.md`**——注入手法+每章配额+禁用区，voice-loop 段落级循环的唯一锚点；经 声口库/README.md「来源仪式」产出并绑定，绑定后全书锁定；②**全书文风基线=`设定/文风.md`**——句长/标点节奏/笔调（chapter-qc-playbook 第七节，原创书前几章后尽早蒸馏）；③**角色台词声口=人物卡声口字段**（三件套）。三层互补不互替，冲突时各管各层。**`设定/声口.md` 为必备项（写作硬闸，铁律 8）**：缺失时初始化不算完成——**新书旧书同走「推荐 1-3 本同频道同赛道参考书 → 作者选定母本 → 炼制 → 绑定」来源仪式**（权威流程见 声口库/README.md「来源仪式」节；旧书不因已有原文豁免，原文只作分寸校准、不作声口主来源），文件头登记绑定信息（绑定书名/来源母本/日期/作者认可）且作者读过认可后才算就绪。没有声口文件，流水线在 N3 前永久停在 `paused_for_human`，一个字的正文都不产出。其余缺项列清单请用户确认补齐方式（回 story-long-write 补 / 现场快速补 / 留空跳过对应门禁项）。

### Step 2：生成章节清单

按卷生成 `大纲/章节清单_第X卷.md`，一章一行：

```markdown
# 卷X章节清单
> 勾选规则：[x] 只能由 N5 在门禁全绿且回写完成后标记
- [ ] C-0001 {章名}（{定位}）｜埋 {伏笔ID}｜回收 {债务}｜{字数预算}
```

定位与伏笔操作从卷纲和 `追踪/伏笔.md` 派生；与卷纲冲突时先修卷纲（大纲五检）。清单是派生视图 + 进度账本的混合体：生成时派生，运行时它的勾选状态就是进度正典。

### Step 3：细纲核查

流水线要求**开跑批次内每章有细纲**（`大纲/细纲_第XXX章.md`，story-long-write 既有协议），且细纲含 beat 级字数预算。缺细纲/缺 beat 预算的章：现在补（推荐，按 story-long-write Phase 3 细纲协议）或标记 `[需细纲]`（N2 进批次时强制补齐）。

### Step 4：初始化管控物

- `控制卡/`、`追踪/门禁/` 空目录
- `追踪/METRICS.md` 表头（| 章 | 轮次 | 门禁失败明细 | 最终字数 | 人工介入 | waive | 成本 | 备注 |，字数一律全码点口径）
- `设定/门禁配置.json`（全书级阈值，默认值：`{"dialog_min":25,"dialog_max":60,"tolerance_pct":2,"dialog_tolerance_pt":3,"long_para_chars":250,"cold_read_mode":"every","author_checkpoint_every":null}`；按题材与用户偏好调整后落盘——对话流题材可上调占比区间；`author_checkpoint_every` 设 N 则每 N 章暂停等作者验收；单章字数区间不在此文件，见控制卡）
- `.flow-status.json` 写 `{"node":"N0","state":"ready","at":"YYYY-MM-DD HH:MM:SS"}`
- 项目非 git 仓库时建议 `git init`（手改检测降级为 mtime 时如实告知精度损失）

### Step 5：汇报与确认

输出：清单章数、缺细纲章数、真值层缺项、`设定/门禁配置.json` 内容（用户可改，改这一个文件即全书生效）。**用户确认后才允许进入 N1**——人审规格是制度性环节，不可省略。

## 存量书接管（续写已有小说）

前提：已有正文若干章（作者手写或他处生成）。接管四步：

1. **逆向重建真值层**：运行 `/story-import` 把已发布正文解析为标准项目结构（设定/大纲/追踪，含伏笔与角色状态回填）。story-flow 不重复实现导入逻辑。
2. **已发布章节入账**：章节清单中把既有章节标为 `- [x] … ｜已发布（导入，未过门禁）`——**已发布正文即正典**（铁律 7 的推论：不重写、不回炉，冲突时以它为准修派生侧）；METRICS 不为其补行。
3. **文风基线量化**：对已发布章节抽 3-5 章跑 check_gate.py，取其指纹（句均字数/单句段占比/对话占比分布）写入 `设定/文风.md` 作为基线——**续写章的指纹漂移对比以作者原文为锚**，这是接管场景独有的优势：写手模仿有量化目标。
4. **声口来源仪式（硬闸，与新书同流程）**：走 声口库/README.md「来源仪式」——推荐 1-3 本同频道同赛道参考书 → 作者选定母本 → 炼制（优先级：库内已校准条目 → 作者提供母本样本拆条目 → 凭认知起草并标注待替换）→ 绑定到 `设定/声口.md`（文件头登记绑定信息，作者认可后全书锁定）。**旧稿原文只用于分寸校准（第 3 步指纹即其载体），不作声口主来源；绑定完成前一章新正文都不写。**
5. **向前规划后进入 N1**：按 story-long-write 卷纲/细纲协议规划后续章节（沿用大纲五检），生成新章清单条目与 `设定/门禁配置.json`（阈值按第 3 步实测基线定，而非默认值），用户确认后续跑。

## 变更模式（剧情改向 / 大纲调整）

触发：用户要求改大纲、改人设、改主线，且清单中已有 `[x]` 章节。

1. **影响面分析**：对比新旧诉求，列出受影响的卷纲段落、细纲、清单条目、伏笔（读 `追踪/伏笔.md` 查哪些已埋伏笔的回收计划被变更打断）。
2. **增量标记**（不推翻已完成章）：清单中新增章 `[+]` 前缀说明、修改章重写细纲并清除旧控制卡、作废章标 `[DROPPED]`（不删除行，保留审计）。
3. **正典冲突扫描**：已完成章节与新大纲的事实冲突逐条列出，分级：可用后文圆的 → 记入 `追踪/伏笔.md`（当补救伏笔管理）；圆不了的 → 决策卡问用户（接受裂缝 / 局部重写该章并重走门禁）。
4. **级联更新**：卷纲 → 细纲 → 清单 → 伏笔账本，全部落盘后输出变更报告，用户确认后恢复流水线。
5. 遵守 story-long-write 大纲锁定规则：已进入正文的前 10 章细纲变更必须经用户确认。
